# 架构与体验决策记录

本文记录 Formula Lab Mission Control 当前已经确认的关键决策。它用于避免后续实现时反复摇摆，也作为进入编码前的产品与架构基线。

## 1. 产品定位

项目名称：

```text
Formula Lab Mission Control
```

中文定位：

```text
SpaceX-inspired 公式识别任务控制台
```

项目不是普通上传工具，也不是课程 demo，而是一个以真实公式识别模型为核心的任务控制台。用户上传公式图片后，系统创建一次可观察、可追踪、可诊断的 Recognition Mission。

## 2. 主设计语言

根目录 [DESIGN.md](../DESIGN.md) 是 UI 设计语言单一来源。

主参考：

```text
awesome-design-md / design-md / spacex / DESIGN.md
```

采用：

- 黑白高对比。
- 固定顶部导航。
- 大写英文微标签。
- 工业感字体。
- 幽灵描边胶囊按钮。
- 深色控制台面板。
- 任务阶段与 telemetry 语言。

不采用：

- 火箭或太空图片。
- 纯营销型 hero。
- 彩色 SaaS 徽章系统。
- 大面积渐变、光晕、粒子背景。

## 3. 页面信息架构

默认打开 Landing，而不是直接进入上传工具。

```text
/                         Landing / Mission Intro
/workbench/               上传工作台
/missions/<uuid>/progress/ Mission 进度页
/missions/<uuid>/report/   Mission Report 结果页
/history/                 Mission Log 历史页
/system/                  Telemetry 系统状态页
```

Landing 负责品牌气质和入口，Workbench 负责真实操作。

外部页面路径和 API 使用 `missions` 命名，内部 Django model 仍然使用 `FormulaJob`。这样用户看到的是 Mission Control 叙事，代码和数据库保持工程清晰。

UUID 只作为内部路由和后台关联标识。用户界面不应把完整 UUID 当作主要 Mission ID 展示，而应使用独立的 `mission_code`。

## 4. Landing 决策

Landing 使用全英文文案。

首屏两个 CTA：

```text
ENTER WORKBENCH
VIEW MISSION LOG
```

视觉背景：

- 使用 AI 生成的电影感主背景图。
- 参考课程公式图片的公式形态，但不直接贴原图。
- 风格偏抽象数学影像：黑底、漂浮公式、几何线、纸张/扫描纹理、冷白光照、少量识别框或 LaTeX 片段。
- 不使用火箭、星球、宇宙飞船等 SpaceX 直译元素。

视觉资产第一版做两张页面图片资产，Workbench 复用全局网格背景：

```text
Landing     完整电影感背景图
其他页面    全局细网格背景
```

视觉资产路径：

```text
static/formulas/visuals/landing-mission-bg.png
```

Landing 背景图第一版只生成桌面宽图：

```text
1920x1100
```

两张页面视觉资产纳入版本库，保证项目开箱后视觉完整。

Landing 使用桌面宽图作为首屏背景，Result 使用轻纹理覆盖。Workbench 与 Mission Log 共用全局网格背景，避免上传工作台和历史页割裂。

Landing 背景通过 `scripts/generate_landing_background.py` 生成。脚本使用 `matplotlib.mathtext` 渲染真实数学公式，再与 Pillow 绘制的测量矩形、扫描线和暗色网格合成，避免背景中出现 `\alpha`、`\delta` 一类未渲染的 LaTeX 源码文本。公式池偏高阶表达，包括广义相对论场方程、薛定谔方程、Maxwell 方程、KL 散度、Fourier 变换、连续性方程和控制系统状态方程。

## 5. Workbench 决策

Workbench 采用英文主标签 + 中文辅助说明。

右侧 telemetry 面板包含：

```text
MODEL STATUS
QUEUE STATUS
SUPPORTED FORMATS
RECENT MISSIONS
```

模型状态：

```text
READY / WARMING / UNKNOWN / ERROR
```

并附带一句简短说明。

队列状态：

```text
ACTIVE count
QUEUED count
LAST DURATION
```

上传方式：

- 点击上传。
- 拖拽上传。
- 第一版不做粘贴图片。

上传流程：

```text
选择 / 拖拽图片
显示图片预览
点击 START RECOGNITION
创建 FormulaJob
进入进度页
```

上传预览区只显示图片预览，不强行展示文件名、大小、格式。

mission 在用户点击 `START RECOGNITION` 时创建，而不是选图预览时创建。

## 6. 进度页决策

进度页使用阶段 checklist + 小进度条。

阶段文案：

```text
UPLOAD LOCKED
QUEUED
MODEL WARMUP
IMAGE PREPROCESS
INFERENCE
LATEX POSTPROCESS
RESULT READY
```

前端显示后端返回的阶段状态，不自行编造最终状态。

## 7. 结果页决策

结果页采用左右分栏。

```text
左侧：原始公式图片 + mission metadata
右侧：LaTeX source console + rendered formula preview
```

LaTeX 展示三种格式：

```text
RAW
BLOCK
INLINE
```

展示方式：

- 使用 tabs 切换。
- 默认选中 `BLOCK`，因为 Markdown/Typora 块公式最适合课程提交和结果展示。
- `COPY CURRENT` 固定在控制台右上角。
- 当前 tab 决定复制内容。
- 复制成功后按钮短暂显示 `COPIED`。
- 渲染预览随当前 tab 同步变化。

## 8. Mission Log 决策

历史页使用时间线，而不是表格或卡片网格。

Mission Log 展示：

- 任务时间。
- 任务状态。
- 公式缩略图。
- LaTeX 摘要。
- 查看结果。
- 复制 LaTeX。
- 失败任务可 Retry。

第一版不支持删除任务，也不支持清空历史。

阶段耗时展示策略：

```text
默认显示总耗时 duration_ms
展开后显示 timings JSON 中的阶段耗时
```

这样 Mission Log 默认保持时间线叙事，展开后提供 telemetry 级诊断细节。

## 9. Retry Mission 决策

第一版只对失败任务提供 Retry Mission。

Retry 行为：

```text
保留失败任务
创建新 FormulaJob
新任务 retry_of 指向原任务
```

数据库字段：

```text
retry_of = ForeignKey("self", null=True, blank=True)
```

Mission Log 可以显示：

```text
RETRY OF <mission code>
```

用户点击 `RETRY MISSION` 后，系统创建新 mission，并直接跳转到新 mission 的进度页。

## 10. Telemetry 决策

Telemetry 页面展示：

- 服务状态。
- 最近任务。
- 简单诊断信息。

内容包括：

```text
Web status
PostgreSQL status + latency
Redis status + latency
Celery worker heartbeat
Recognition model status
Last mission code/status/duration
Queue length
Media storage writable
Recent error
```

Telemetry 允许展示 Django、PostgreSQL、Redis、Celery、PaddleOCR、pix2tex 等技术名词；主产品页面不把这些技术名词当装饰。

`WARMUP MODEL` 只放在 Telemetry 页面，不放在 Landing 或 Workbench。

Telemetry 第一版不做登录保护，因为项目是本地课程验收和开发环境工具。

## 13. 模型与任务决策

真实模型路线：

- 本机默认使用 PaddleOCR Formula Recognition。
- 默认模型为 `PP-FormulaNet_plus-S`。
- 保留 pix2tex / LaTeX-OCR 作为对照和回退。
- 不对课程图片硬编码。
- 模型失败不 fallback 到 mock。

模型加载：

- worker 启动时不强制加载。
- 第一次识别时懒加载。
- Telemetry 页面提供 `WARMUP MODEL`。
- Warmup 不保存到 Mission Log。

模型状态保存到 Redis：

```text
formula_lab:model:status
formula_lab:model:message
formula_lab:model:last_warmup_at
formula_lab:model:last_error
```

Celery：

- Redis 作为 broker。
- 不使用 Celery result backend。
- `CELERY_TASK_IGNORE_RESULT=True`。
- 业务结果统一写 PostgreSQL。

Worker heartbeat：

```text
formula_lab:worker:heartbeat
```

由 worker 定期写入 Redis，TTL 建议 30 或 60 秒。

## 14. 上传与图片处理决策

支持格式：

```text
PNG
JPG
JPEG
```

上传大小限制：

```text
10MB
```

图片预处理：

- 保留原始上传图用于展示。
- 模型使用预处理后的临时图。
- 超过最大边长才缩放，建议最大边长 1600px。
- 透明 PNG 合成白底。

## 15. 错误处理决策

模型失败时：

- 不 fallback。
- 不 mock。
- 保存失败状态。

页面展示：

```text
错误摘要 + 可展开技术详情
```

字段：

```text
error_message   用户级摘要
error_detail    截断后的 traceback
failure_stage   失败阶段
```

`error_detail` 最多保存 4000 字符，超长追加：

```text
... [truncated]
```

失败阶段建议：

```text
upload_validation
queue_dispatch
model_warmup
image_preprocess
inference
latex_postprocess
database_update
unknown
```

## 16. FormulaJob 字段决策

第一版核心字段包括：

```text
id
mission_code
original_image
preprocessed_image
status
progress
stage_code
stage_label
stage_message
latex_result
engine_name
retry_of
error_message
error_detail
failure_stage
created_at
started_at
finished_at
duration_ms
timings
```

`id` 使用 UUID，负责数据库主键、URL 路由和 Celery 参数。它不适合作为用户界面主标识，因为完整 UUID 看起来像哈希码。

`mission_code` 是用户可读标识，用于进度页、结果页和 Mission Log。推荐格式：

```text
FL-YYYYMMDD-0001
```

示例：

```text
FL-20260519-0007
```

当前实现策略：

- 新增 `mission_code = CharField(max_length=32, unique=True, db_index=True)`。
- 创建任务时生成，不依赖用户输入。
- UI 模板优先显示 `mission_code`。
- API 同时返回 `id` 和 `mission_code`。
- 第一阶段 URL 可以继续使用 UUID，避免大范围路由重构；第二阶段如果需要更产品化，可增加 `/missions/<mission_code>/...` 路由。

不保存 confidence，因为当前模型链路未必提供可靠置信度。

`engine_name` 第一版默认：

```text
paddle
```

阶段耗时保存到 JSONField：

```json
{
  "model_warmup_ms": 820,
  "image_preprocess_ms": 43,
  "inference_ms": 1250,
  "latex_postprocess_ms": 12,
  "total_ms": 2125
}
```

## 17. 测试与验收决策

测试策略：

```text
Django 单元测试 + Playwright 浏览器测试
```

Playwright E2E 使用真实公式识别模型，不使用 mock。本机默认使用 PaddleOCR Formula Recognition。

Playwright E2E 默认跑课程提供的四张测试图片：

```text
linux2026/大实验2/测试用图片/formular1.png
linux2026/大实验2/测试用图片/formular2.png
linux2026/大实验2/测试用图片/formular3.png
linux2026/大实验2/测试用图片/formular4.png
```

命令分层：

```text
make verify   检查服务健康，不跑真实模型 E2E
make warmup   预热当前识别模型
make local    本机启动 Redis + Django + Celery，默认 PaddleOCR
make e2e      跑 Playwright + 真实模型端到端测试
make test     跑 Django 单元测试
```

真实模型 E2E 不包含在 `make verify` 中，避免健康检查过慢。
