# 架构与体验决策记录

本文记录 Formula Lab Mission Control 当前已经确认的关键决策。它用于避免后续实现时反复摇摆，也作为进入编码前的产品与架构基线。

## 1. 产品定位

项目名称：

```text
Formula Lab Mission Control
```

中文定位：

```text
SpaceX-inspired 公式识别、审校与导出工作台
```

项目不是普通上传工具，也不是课程 demo，而是一个以真实公式识别模型为核心的任务控制台。用户上传公式图片后，系统创建一次可观察、可追踪、可诊断的 Recognition Mission；当任务挂载到项目时，识别结果会沉淀为论文工作区中的 FormulaItem。

## 2. 主设计语言

根目录 [DESIGN.md](../DESIGN.md) 是 UI 设计语言单一来源。

主参考：

```text
awesome-design-md / design-md / spacex / DESIGN.md
```

采用：

- 黑白高对比。
- 固定顶部导航。
- 大写英文微标签。
- 工业感字体。
- 幽灵描边胶囊按钮。
- 深色控制台面板。
- 任务阶段与 telemetry 语言。

不采用：

- 火箭或太空图片。
- 纯营销型 hero。
- 彩色 SaaS 徽章系统。
- 大面积渐变、光晕、粒子背景。

## 3. 页面信息架构

默认打开 Landing，而不是直接进入上传工具。

```text
/                         Landing / Mission Intro
/workbench/               上传工作台
/projects/                Projects 项目索引
/projects/<uuid>/         Project Workspace 项目工作区
/missions/<uuid>/progress/ Mission 进度页
/missions/<uuid>/report/   Mission Report 结果页
/history/                 Mission Log 历史页
/system/                  Telemetry 系统状态页
```

Landing 负责品牌气质和入口，Workbench 负责真实操作。

外部页面路径和 API 使用 `missions` 命名，内部 Django model 仍然使用 `FormulaJob`。这样用户看到的是 Mission Control 叙事，代码和数据库保持工程清晰。

UUID 只作为内部路由和后台关联标识。用户界面不应把完整 UUID 当作主要 Mission ID 展示，而应使用独立的 `mission_code`。

## 4. Product Core Foundation 状态

Product Core Foundation 已经从单次识别任务走向 Projects-first 产品结构。第一片产品核心围绕三个实体展开：

```text
PaperProject
  -> BatchMission
    -> FormulaItem
      -> optional FormulaJob
```

第一片页面能力是 `/projects/` 项目索引和 `/projects/<uuid>/` 项目工作区。它们负责展示项目、批次、公式条目、公式队列、Formula Inspector、Workflow Status、Review Drawer、Paper Fit Preview 和项目级 `.tex/.md` 导出，保留现有 `/workbench/` 单次识别流程。

当前已经完成：

- Workbench 创建或选择 PaperProject。
- 识别成功后自动沉淀 FormulaItem。
- Project Workspace 展示公式队列与 Inspector。
- Review Drawer 支持单条 LaTeX 编辑、实时预览和确认。
- 项目级 `.tex/.md` 即时下载。
- Paper Fit Preview 使用前端 layout intelligence 做论文栏宽适配提示。

下一阶段仍未完成：

- Crop Studio。
- 持久化 ExportArtifact。
- Symbol Intelligence。
- 本地 AI 解释、检查和修复。

## 5. Landing 决策

Landing 使用全英文文案。

首屏两个 CTA：

```text
ENTER WORKBENCH
VIEW MISSION LOG
```

视觉背景：

- 使用 AI 生成的电影感主背景图。
- 参考课程公式图片的公式形态，但不直接贴原图。
- 风格偏抽象数学影像：黑底、漂浮公式、几何线、纸张/扫描纹理、冷白光照、少量识别框或 LaTeX 片段。
- 不使用火箭、星球、宇宙飞船等 SpaceX 直译元素。

视觉资产第一版做两张页面图片资产，Workbench 复用全局网格背景：

```text
Landing     完整电影感背景图
其他页面    全局细网格背景
```

视觉资产路径：

```text
static/formulas/visuals/landing-mission-bg.png
```

Landing 背景图第一版只生成桌面宽图：

```text
1920x1100
```

两张页面视觉资产纳入版本库，保证项目开箱后视觉完整。

Landing 使用桌面宽图作为首屏背景，Result 使用轻纹理覆盖。Workbench 与 Mission Log 共用全局网格背景，避免上传工作台和历史页割裂。

Landing 背景通过 `scripts/generate_landing_background.py` 生成。脚本使用 `matplotlib.mathtext` 渲染真实数学公式，再与 Pillow 绘制的测量矩形、扫描线和暗色网格合成，避免背景中出现 `\alpha`、`\delta` 一类未渲染的 LaTeX 源码文本。公式池偏高阶表达，包括广义相对论场方程、薛定谔方程、Maxwell 方程、KL 散度、Fourier 变换、连续性方程和控制系统状态方程。

## 6. Workbench 决策

Workbench 采用英文主标签 + 中文辅助说明。

右侧 telemetry 面板包含：

```text
MODEL STATUS
QUEUE STATUS
RECENT MISSIONS
```

模型状态：

```text
READY / WARMING / UNKNOWN / ERROR
```

并附带一句简短说明。

队列状态：

```text
ACTIVE count
QUEUED count
LAST DURATION
```

上传方式：

- 点击上传。
- 拖拽上传。
- 第一版不做粘贴图片。

上传流程：

```text
选择 / 拖拽图片
显示图片预览
点击 START RECOGNITION
创建 FormulaJob
进入进度页
```

上传预览区只显示图片预览，不强行展示文件名、大小、格式。

mission 在用户点击 `START RECOGNITION` 时创建，而不是选图预览时创建。

## 8. 结果页决策

结果页采用左右分栏。

```text
左侧：原始公式图片 + mission metadata
右侧：KaTeX Preview + Paper Fit Preview + LaTeX source console
```

LaTeX 展示三种格式：

```text
RAW
BLOCK
INLINE
```

展示方式：

- 使用 tabs 切换。
- 默认选中 `BLOCK`，因为 Markdown/Typora 块公式最适合课程提交和结果展示。
- 复制按钮固定在控制台操作区，当前使用图标按钮。
- 当前 tab 决定复制内容。
- 复制成功后按钮短暂反馈。
- 渲染预览随当前 tab 同步变化。

Paper Fit Preview 是辅助模块，用于表达公式在论文栏宽中的适配情况。它不应成为视觉主角，也不应使用抢眼大白卡。当前策略是低权重暗色 telemetry strip，保持可读但让 KaTeX Preview 和 LaTeX Source 成为主内容。

## 9. Mission Log 决策

历史页使用时间线，而不是表格或卡片网格。

Mission Log 展示：

- 任务时间。
- 任务状态。
- 公式缩略图。
- LaTeX 摘要。
- 查看结果。
- 复制 LaTeX。
- 失败任务可 Retry。

第一版不支持删除任务，也不支持清空历史。

阶段耗时展示策略：

```text
默认显示总耗时 duration_ms
展开后显示 timings JSON 中的阶段耗时
```

这样 Mission Log 默认保持时间线叙事，展开后提供 telemetry 级诊断细节。

## 10. Retry Mission 决策

第一版只对失败任务提供 Retry Mission。

Retry 行为：

```text
保留失败任务
创建新 FormulaJob
新任务 retry_of 指向原任务
```

数据库字段：

```text
retry_of = ForeignKey("self", null=True, blank=True)
```

Mission Log 可以显示：

```text
RETRY OF <mission code>
```

用户点击 `RETRY MISSION` 后，系统创建新 mission，并直接跳转到新 mission 的进度页。

## 14. 模型与任务决策

真实模型路线：

- 本机默认使用 PaddleOCR Formula Recognition。
- 默认模型为 `PP-FormulaNet_plus-S`。
- 保留 pix2tex / LaTeX-OCR 作为对照和回退。
- 不对课程图片硬编码。
- 模型失败不 fallback 到 mock。

模型加载：

- worker 启动时不强制加载。
- 第一次识别时懒加载。
- Telemetry 页面提供 `WARMUP MODEL`。
- Warmup 不保存到 Mission Log。

模型状态保存到 Redis：

```text
formula_lab:model:status
formula_lab:model:message
formula_lab:model:last_warmup_at
formula_lab:model:last_error
```

Celery：

- Redis 作为 broker。
- 不使用 Celery result backend。
- `CELERY_TASK_IGNORE_RESULT=True`。
- 业务结果统一写 PostgreSQL。

Worker heartbeat：

```text
formula_lab:worker:heartbeat
```

由 worker 定期写入 Redis，TTL 建议 30 或 60 秒。

## 16. 错误处理决策

模型失败时：

- 不 fallback。
- 不 mock。
- 保存失败状态。

页面展示：

```text
错误摘要 + 可展开技术详情
```

字段：

```text

error_detail    截断后的 traceback
failure_stage   失败阶段
```

`error_detail` 最多保存 4000 字符，超长追加：

```text
... [truncated]
```

失败阶段建议：

```text
upload_validation
queue_dispatch
model_warmup
image_preprocess
inference
latex_postprocess
database_update
unknown
```

## 17. FormulaJob 字段决策

第一版核心字段包括：

```text
id
mission_code
original_image
preprocessed_image
status
progress
stage_code
stage_label
stage_message
latex_result
engine_name
retry_of
error_message
error_detail
failure_stage
created_at
started_at
finished_at
duration_ms
timings
```

`id` 使用 UUID，负责数据库主键、URL 路由和 Celery 参数。它不适合作为用户界面主标识，因为完整 UUID 看起来像哈希码。

`mission_code` 是用户可读标识，用于进度页、结果页和 Mission Log。推荐格式：

```text
FL-YYYYMMDD-0001
```

示例：

```text
FL-20260519-0007
```

当前实现策略：

- 新增 `mission_code = CharField(max_length=32, unique=True, db_index=True)`。
- 创建任务时生成，不依赖用户输入。
- UI 模板优先显示 `mission_code`。
- API 同时返回 `id` 和 `mission_code`。
- 第一阶段 URL 可以继续使用 UUID，避免大范围路由重构；第二阶段如果需要更产品化，可增加 `/missions/<mission_code>/...` 路由。

不保存 confidence，因为当前模型链路未必提供可靠置信度。

`engine_name` 第一版默认：

```text
paddle
```

阶段耗时保存到 JSONField：

```json
{
  "model_warmup_ms": 820,
  "image_preprocess_ms": 43,
  "inference_ms": 1250,
  "latex_postprocess_ms": 12,
  "total_ms": 2125
}
```

```text
linux2026/大实验2/测试用图片/formular1.png
```

命令分层：


## 19. 文档治理决策

Formula Lab 不再为每次讨论新增孤立文档。所有新增决策优先合并到既有文档：

- 运行、部署和验证入口写入 `README.md` 或 `docs/08-Docker运行方案.md`。
- UI 设计语言写入 `DESIGN.md` 和 `docs/10-UIUX设计语言.md`。
- 产品、架构和体验决策写入本文档。
- 数据模型写入 `docs/04-数据模型.md`。
- 测试策略写入 `docs/09-测试与验收标准.md`。

旧的 agent 执行计划不作为长期项目文档保留，避免计划文档和真实代码状态分叉。

历史执行计划统一放入：

```text
docs/superpowers/plans/archive/
```

当前活跃架构治理入口只保留：

```text
docs/superpowers/specs/2026-05-20-架构治理升级设计.md
docs/superpowers/plans/2026-05-20-architecture-governance-upgrade.md
```

Repository governance checker 用于约束运行时缓存、媒体目录、虚拟环境和大文件边界。它不替代人工架构判断，但作为日常开发的低成本护栏，避免 `.conda/`、`node_modules/`、模型缓存、媒体文件和过大的手写源码被误纳入版本库。

## 20. 下一阶段产品架构升级

Formula Lab 下一阶段方向从单张公式 OCR 工具升级为：

```text
Paper Math Assistant + LaTeX Formula Workbench
```

核心产品不做泛论文 AI，而围绕公式资产构建：

- 识别公式。
- 校对公式。
- 管理公式。
- 解释公式。
- 导出公式。
- 验证公式质量。

信息架构采用 Projects-first：

```text
PaperProject
  -> BatchMission
    -> FormulaItem
      -> ExportArtifact
      -> SymbolInsight
```

所有 Batch 必须属于一个 Paper Project；Quick Capture 也在项目内发生，不创建无归属任务。

核心工作流采用 Split Lane：

```text
上传图片
-> 智能判断是否建议进入 Crop Studio
-> 手动框选 + 排序
-> 批量识别
-> quality_score / quality_flags
-> READY 自动进入可导出区
-> REVIEW / FIX 进入 Review Drawer
-> 确认后导出 .tex / .md 文件
```

当前已落地的重要界面能力：

- Project 首页使用论文工作台视图，展示项目概览、Formula Inspection Queue、Formula Inspector、Workflow Status、Recent Batches、Symbol Intelligence 和 Export Files。
- Review 使用列表 + 右侧 Review Drawer。
- Formula Item 状态采用 `auto_ready / needs_review / edited / confirmed / exported / rejected`。
- 列表保持紧凑可扫读，详细 `quality_score`、`quality_flags` 和后续 AI 建议放在 Inspector 或 Review Drawer。
- 当前 Review Drawer 使用普通 textarea 保持实现轻量；后续如果公式编辑复杂度上升，再升级到 CodeMirror。
- 导出以文件为主，优先生成 `.tex` 和 `.md`，可选择是否包含 metadata comments。

下一阶段仍建议补齐：

- Crop Studio 第一版支持手动框选和排序，不做自动切分强依赖。
- ExportArtifact 持久化，记录导出历史、格式和时间。
- SymbolInsight 从占位区变成真实符号表和一致性提示。

本地 AI 采用增强层，而不是系统硬依赖：

- 优先适配 Ollama、LM Studio 或本地 OpenAI-compatible endpoint。
- V1 放在 Review Drawer，提供 `EXPLAIN FORMULA`、`EXPLAIN SYMBOLS`、`CHECK LATEX`、`SUGGEST FIX`。
- OCR、校对和导出流程必须在没有本地 LLM 时仍可运行。

架构路线采用 Product Core Refactor，但吸收平台化服务边界：

```text
Product entities: PaperProject / BatchMission / FormulaItem / ExportArtifact / SymbolInsight
Service modules: OCR Service / Quality Service / Export Service / Local AI Service / Symbol Service
```

## 21. Pretext 启发与落地边界

[chenglou/pretext](https://github.com/chenglou/pretext) 的直接价值不是公式 OCR，而是它处理复杂文本排版时的工程纪律：预处理、热路径复用、benchmark、canary 和跨渲染目标一致性。

Formula Lab 已经在前端构建链中引入 `@chenglou/pretext`，但只作为布局测量和预览辅助能力，不作为 OCR、KaTeX 渲染或完整 TeX 排版引擎。可借鉴的技术方式是：

```text
recognize: 昂贵 OCR
normalize: LaTeX 规整
quality: 质量评分与 flags
preview: KaTeX / 论文环境预览
export: Markdown / LaTeX / align / inline 文件生成
```

对应到 Pretext 的思想：

```text
prepare once, reuse often
```

因此 `FormulaItem` 后续不应只保存一个 `latex_result`，而应逐步保存可复用中间状态：

- 原始 OCR 输出。
- 规整后的 LaTeX。
- 当前人工编辑版本。
- KaTeX 渲染状态。
- `quality_score`。
- `quality_flags`。
- 导出格式缓存。
- 最近一次导出目标。

Pretext 技术可在以下位置局部落地：

- **Export Preview**：在浏览器端预估 Markdown、LaTeX article、thesis、two-column 等导出视图中，公式前后文本、注释、符号说明是否溢出或换行异常。
- **Review List 稳定布局**：批量公式列表中 LaTeX 摘要、AI 建议、错误说明长度不一时，用文本测量或类似策略减少布局跳动。
- **Quality Canary Set**：维护一组困难公式样例，覆盖矩阵、分段函数、多行推导、长分式、低清截图和论文 PDF 截图，用于识别质量回归。
- **Quality Dashboard**：System 页面后续不只看 Redis/Celery/Paddle 状态，也看 canary pass rate、KaTeX error rate、needs review ratio 和平均识别耗时。
- **Research Log 内聚到决策记录**：记录模型切换、失败样例、质量评分策略和被否掉的方案，但不再新增分散文档。

## 22. 下一轮架构治理决策

下一轮架构升级优先解决“页面变大”和“职责重新粘连”的问题，而不是引入新框架。

优先级：

1. **CSS 分层治理**：拆分 `projects.css`、`result-inspector.css`、`workbench.css`，让页面布局、公式队列、Paper Fit、Workflow Status、上传区和 telemetry 组件各自成文件。
2. **JS 模块治理**：Project Workspace、Result 和 System 已拆入目录模块；下一步治理 Workbench 上传状态脚本，以及把 CSS 大组件继续按视觉职责切开。
3. **Django 页面层治理**：Projects 与 Project Workspace 已把查询和页面上下文下沉到 selectors/presenters；下一步把审校确认、导出状态流转和 artifact 生成收敛进 services。
4. **Project Workspace contract**：workspace overview、review data、paper preview data、pagination、status filters 和 completion_rate 已形成 presenter contract，后续继续补 artifact/export contract。
5. **Governance checker 扩展**：继续约束运行时缓存、媒体文件、虚拟环境、大文件和生成物边界，防止项目继续膨胀。

本轮不建议做：

- 引入 React/Vue。
- 替换 Django Template。
- 重新设计数据库主键或 URL。
- 把 Pretext 扩展成完整排版引擎。
- 做 PDF 编译服务。

Pretext demos 对 Formula Lab 的具体启发：

- `bubbles / shrinkwrap`：用于 Formula Item 列表中的 LaTeX 摘要、错误摘要和 AI 建议气泡。目标是让多行文本尽可能紧凑，减少右侧空白和列表高度浪费。
- `accordion`：用于 Review Drawer 中的质量 flags、技术错误、识别 timings 等可展开区块。高度在展开前可预测，避免抽屉内容跳动。
- `dynamic-layout / editorial-engine`：用于 Paper Export Preview。未来可做论文片段预览，模拟标题、正文、公式、符号说明、注释在固定页面宽度内的流动效果。
- `rich-note`：用于符号解释和 inline formula notes。普通文字、代码片段、公式 token、状态 chip 可以在同一行自然换行，chip 保持不可断开。
- `markdown-chat`：用于本地 AI 校对建议流。长建议列表和 Markdown 内容可以虚拟化，避免 AI 输出变多后页面卡顿。
- `masonry`：用于 Project 首页的公式资产概览或质量问题墙。每张公式卡片高度不同，但不依赖 DOM 反复测量。
- `justification-comparison`：用于导出质量预览。不是要重做 TeX 排版，而是让用户看到某些公式放入双栏或窄栏时的间距、换行和溢出风险。

落地优先级：

```text
P0: 不加依赖，先用 CSS 和固定高度策略把当前 UI 稳住。
P1: 引入 @chenglou/pretext 到前端构建链，用于 Review List 文本高度预测和 shrinkwrap 摘要。
P2: 做 Export Preview，预测 .md / .tex 注释和公式说明在目标宽度下的布局风险。
P3: 做 rich inline notes，把符号解释、公式 token、状态 chip 和 AI 建议组成更自然的论文工作台文本流。
```

Implementation status: 已落地的切片包括 Mission Log summary stabilization、Project Workspace Paper Fit Preview、Review Drawer、项目级 `.tex` / `.md` 即时导出、报告页 KaTeX preview helper 拆分，以及 Mission Report 中低权重 Paper Fit Preview。当前仍避免把 Pretext 扩展为完整论文排版引擎。

边界：

- 公式本体渲染仍交给 KaTeX。
- OCR 准确率仍由 PaddleOCR、图片预处理、质量评分和人工校对共同保证。
- Pretext 类能力只用于“论文导出预览、文本测量、布局稳定性、质量回归纪律”，不把项目带偏成通用排版引擎。
