## config 模块

`config` 是 Django 项目配置层，负责全局配置。第一版采用多文件 settings：

```text
config/settings/base.py
config/settings/dev.py
config/settings/prod.py
```

主要职责：

- 读取环境变量。
- 配置数据库连接。
- 配置 Redis 和 Celery。
- 配置静态文件和媒体文件路径。
- 配置 URL 根路由。

建议把 Celery 初始化放在 `config/celery.py`，让 worker 和 web 使用同一套 Django settings。

## formulas 应用模块

`apps/formulas` 是项目的核心业务应用。

它负责：

- 上传公式图片。
- 创建识别任务。
- 查询任务进度。
- 展示识别结果。
- 展示历史记录。
- 管理公式识别相关的数据模型。

## models.py

`models.py` 定义业务模型。第一版核心模型是 `FormulaJob`，用于表示一次公式图片识别任务。

模型不应包含复杂模型推理逻辑，但可以包含轻量的状态判断方法，例如：

- 是否已完成。
- 是否失败。
- 是否还在运行。
- 计算任务耗时。

## views 目录

`apps/formulas/views/` 负责页面和 HTTP API 编排。项目已经从单个 `views.py` 拆成按页面域划分的模块：

```text
workbench_views.py  上传工作台、创建任务
mission_views.py    进度页、结果页、历史页、重试和 mission API
project_views.py    Projects、Project Workspace、审校和导出
system_views.py     Telemetry 系统状态
shared.py           页面层共享工具
```

它应该做：

- 校验上传表单。
- 保存上传文件。
- 创建任务记录。
- 投递 Celery 任务。
- 返回页面或 JSON。
- 把 request 的 query/path 交给 presenter，而不是在 view 内拼装完整页面模型。

它不应该做：

- 直接调用 PaddleOCR 或 pix2tex。
- 直接执行耗时推理。
- 处理复杂图片预处理。
- 拼装过厚的页面上下文；复杂查询应下沉到 selectors，展示上下文应下沉到 presenters。当前 Projects 与 Project Workspace 的页面骨架、overview、最近 batch 和 paper preview payload 已经从 `project_views.py` 下沉；公式 Review Inbox 的列表、筛选和编辑状态由 React island 通过 JSON API 获取。

## selectors 与 presenters

`selectors/` 是查询层，负责把页面需要的数据用可复用、可测试的查询表达出来。它不负责 HTML 文案，也不执行写操作。

`presenters/` 是页面展示上下文层，负责把模型对象转换成模板可直接使用的数据结构。它适合承载：

- Projects 的 card metrics、latest batch 摘要。
- Project Workspace 的 overview、最近批次、轻量 paper preview data 和 React mount 配置。
- Mission Report 的格式化 LaTeX、耗时、状态展示。
- 后续 Quality Dashboard 的指标摘要。

下一轮架构升级应优先把写操作也收敛进 services，例如 FormulaItem 审校确认、导出状态流转和项目级 artifact 生成，避免 view 文件重新变厚。

## tasks.py

`tasks.py` 定义 Celery 后台任务。

它负责：

- 从数据库读取任务。
- 更新任务状态和进度。
- 调用识别服务。
- 保存 LaTeX 结果。
- 捕获异常并写入错误信息。

## services 目录

`services` 是识别与处理能力的封装层。

建议模块：

- `recognizer.py`：统一识别入口，向业务层提供稳定接口。
- `ocr_engines.py`：识别引擎工厂，根据配置选择 PaddleOCR 或 pix2tex。
- `paddle_formula_engine.py`：PaddleOCR Formula Recognition 具体适配器。
- `pix2tex_engine.py`：pix2tex 具体适配器，用于对照和回退。
- `preprocessing.py`：图片格式、尺寸、透明背景等预处理。
- `latex_formats.py`：LaTeX 文本清洗、包裹符号处理和显示修正。
- `export_artifacts.py`：项目级 `.tex` 与 `.md` 即时导出文本生成。
- `project_items.py`：FormulaItem 审校确认等项目内写操作。
- `health.py`：系统状态检查。
- `model_state.py`：模型状态读写和 UI 状态映射。
- `telemetry.py`：worker heartbeat 等轻量 telemetry 工具。

服务层的目标是隔离第三方模型依赖，让业务层不直接绑定 PaddleOCR 或 pix2tex 的内部 API。

## 前端分层

Formula Lab 当前不是单一前端范式，而是按复杂度分层：

- **Django Template**：承载多页面路由、页面骨架、SEO 友好的首屏 HTML 和课程验收路径。
- **原生 JavaScript 页面模块**：负责 Workbench、Progress、Mission Report、Mission Log、System 等工具页交互。
- **React workspace editor island**：只在 Project Workspace 内承载论文编辑、Formula Review Inbox、CodeMirror、版本时间线和文件操作。
- **React landing island**：只在 Landing 内承载 GSAP / Three.js / scroll story 等高复杂度动效。
- **Pretext layout intelligence**：作为布局测量与稳定性辅助，不进入 OCR 业务真相链路。
- **Vite generated assets**：`frontend/` 是源码，`apps/formulas/static/formulas/**/generated/` 是构建产物，二者需要保持同步。

这套结构的目标是保留 Django 多页面系统的稳定性，同时允许少数高复杂度界面使用现代前端工具。React 不是全站 SPA 替代品；它只出现在 Landing 和 Project Workspace 这两个复杂交互岛。

## templates 与 static

模板负责页面结构，静态文件负责样式与交互。

前端资源约定：

- Tailwind CDN 用于旧模板中的基础布局和 utility；新增复杂前端优先使用本地 CSS 与 Vite 构建链。
- 本地 CSS 负责 Formula Lab 的 SpaceX-inspired 设计语言。
- CSS 使用 `base.css + pages/*.css`。
- JS 按页面拆分。
- `frontend/formulas/layout_intelligence.js` 是 Pretext 源文件，构建后输出到 `static/formulas/js/generated/layout-intelligence.js`。
- `frontend/formulas/landing/` 是 Landing 的 React / GSAP / Three.js 源码，构建后输出到 `static/formulas/js/generated/landing*.js` 与 `static/formulas/css/generated/landing.css`。
- `frontend/formulas/workspace_editor/` 是 Project Workspace 的 React / CodeMirror 源码，构建后输出到 `static/formulas/js/generated/workspace-editor.js` 与 `static/formulas/js/generated/codemirror.js`。
- 视觉资产放在 `static/formulas/visuals/`；除 Landing 外，Workbench、Mission Log、Progress、Result、System 全部使用全局细网格背景，不单独引用图片纹理。

第一版页面包括：

- 首页：产品入口。
- Workbench：上传图片，选择 Existing Project 或 New Project。
- Projects：论文项目索引。
- Project Workspace：项目内批次、React Review Inbox、论文文件编辑、Paper Fit Preview、Workflow Status 和导出入口。
- 进度页：展示任务阶段与进度条。
- 结果页：展示原图、LaTeX 文本、公式渲染、一键复制。
- 历史记录页：展示所有历史识别任务。
- 系统状态页：展示 Web、数据库、Redis、Worker、模型与媒体文件状态。

## 当前架构风险文件

当前已有 governance checker 约束大文件，但仍有一些文件接近继续拆分的临界点。下一轮架构升级应优先处理：

```text
apps/formulas/static/formulas/css/pages/projects.css
apps/formulas/static/formulas/css/pages/result-inspector.css
apps/formulas/static/formulas/css/pages/workbench.css
```

拆分原则不是为了追求文件数量，而是让每个文件围绕一个稳定职责：页面布局、组件样式、paper fit telemetry、workspace sidebar、export actions、数据查询或页面 presenter。Formula Review Inbox 已迁入 React editor island，旧的服务端 formula queue、formula inspector 和 review drawer 前端资产已移除，避免同一工作区存在两套公式审阅入口。React editor island 采用 `components/` + `hooks/` + `lib/` 分层：`EditorIsland.tsx` 只负责组合组件，公式审查状态放在 `useFormulaReview.ts`，论文文件主状态放在 `usePaperDocuments.ts`，文件弹窗与删除副作用分别放在 `usePaperFileDialog.ts` 和 `usePaperFileDelete.ts`，纯文本生成与公式插入逻辑放在 `paperFileContent.ts`。当前 `paper-fit-preview.css`、`project-paper-preview.css`、`project-workspace-sidebar.css`、`static/formulas/js/project_workspace/`、`static/formulas/js/result/` 和 `static/formulas/js/system/` 已经从较大的页面文件中拆出，后续继续按同样方式治理 Workbench 和剩余页面 CSS。
