# 公式识别引擎

## 技术选择

第一版本机开发默认选择 PaddleOCR Formula Recognition 作为真实公式识别引擎，模型为：

```text
PP-FormulaNet_plus-S
```

选择原因：

- 目标与项目高度匹配：公式图片转 LaTeX。
- Python 生态可用，适合 Django 与 Celery 集成。
- 能体现真实模型识别能力，而不是只对测试图片做映射。
- 对课程测试图片的识别效果优于当前 pix2tex 路径，尤其是 `formular4.png` 这类集合、根号和循环小数混合表达。

`pix2tex / LaTeX-OCR` 继续保留为兼容引擎，用于对照、回退和后续模型评测。

## 识别层边界

pix2tex 不直接写在 Django view 中，而是封装在服务层。

建议结构：

```text
services/
  recognizer.py
  recognition_clients.py
  recognition_types.py
  model_api_client.py
  ocr_engines.py
  paddle_formula_engine.py
  pix2tex_engine.py
  preprocessing.py
  latex_formats.py
```

业务代码先调用 recognition client：

```python
client = get_recognition_client()
result = client.recognize(image_path)
```

client 后端由配置决定：

```text
FORMULA_LAB_RECOGNITION_BACKEND=local  直接调用本地 Paddle / pix2tex engine
FORMULA_LAB_RECOGNITION_BACKEND=http   通过 FastAPI model-api 调用模型服务
```

这样可以让 Web 层、任务层和模型层保持解耦，也让 Docker/Linux 部署时可以把重模型隔离到独立服务。

## recognizer.py

`recognizer.py` 是识别入口。

职责：

- 接收图片路径。
- 调用图片预处理。
- 调用 recognition client。
- 调用 LaTeX 后处理。
- 返回最终 LaTeX 文本。

它不关心 HTTP 请求，也不直接操作页面。

## recognition_clients.py

`recognition_clients.py` 是识别调用边界。

可选后端：

```text
local  本地 engine，适合 Mac 本机开发和快速回滚
http   FastAPI model-api，适合 Docker Compose 和 Linux 部署
```

`LocalRecognitionClient` 继续复用 `ocr_engines.py`；`ModelApiRecognitionClient` 使用 multipart 上传图片到：

```text
POST /v1/formula/recognize
```

返回统一的 `RecognitionResult`：

```text
latex
engine
model
duration_ms
confidence
```

Celery task 只消费这个结果，不关心底层到底是本地模型还是 HTTP 服务。

HTTP client 会保留模型服务错误的 `status_code` 和 `code`，例如 `MODEL_WARMUP_FAILED`、`MODEL_INFERENCE_FAILED`。第一版仍然把任务标记为 failed，但后续可以基于这些结构化错误扩展重试策略。

## FastAPI model-api

`model_service/` 是独立模型服务入口：

```text
GET  /health
GET  /models/current
POST /warmup
POST /v1/formula/recognize
```

`/health` 不是简单的进程存活探针，而是模型 readiness：未预热返回 `503`，预热成功后返回 `200`。Docker Compose 通过 `POST /warmup` 做 healthcheck，让 worker 等待模型可用后再处理队列任务。

## ocr_engines.py

`ocr_engines.py` 是识别引擎工厂，读取配置项：

```text
FORMULA_LAB_OCR_ENGINE=paddle
```

可选值：

```text
paddle
pix2tex
```

业务层不直接 new 第三方模型，而是通过工厂获得统一接口。这样后续替换模型不会影响 Django view、Celery task 和页面逻辑。

## paddle_formula_engine.py

`paddle_formula_engine.py` 是 PaddleOCR Formula Recognition 适配器。

职责：

- 初始化 PaddleOCR `FormulaRecognition`。
- 使用 `PP-FormulaNet_plus-S` 执行公式识别。
- 将 PaddleOCR 结果对象解析为 LaTeX 字符串。
- 将 PaddleX 模型缓存放在项目 `.model-cache/paddlex/` 下。
- 默认使用 BOS 模型源并跳过启动时的模型源连通性检查，减少本机启动阻塞。

关键配置：

```text
FORMULA_LAB_PADDLE_MODEL_NAME=PP-FormulaNet_plus-S
FORMULA_LAB_PADDLE_DEVICE=cpu
FORMULA_LAB_PADDLE_CACHE_HOME=.model-cache/paddlex
FORMULA_LAB_PADDLE_MODEL_SOURCE=BOS
FORMULA_LAB_PADDLE_DISABLE_SOURCE_CHECK=True
```

## pix2tex_engine.py

`pix2tex_engine.py` 是 pix2tex 适配器。

职责：

- 初始化 pix2tex 模型。
- 管理模型加载。
- 对单张图片执行识别。
- 将第三方库异常转换为项目内部错误。

模型加载可能较慢，因此 worker 启动后可以采用懒加载策略：第一次识别时加载模型，后续任务复用同一个模型对象。

## preprocessing.py

图片预处理负责提高识别稳定性。

第一版可以包含：

- 检查图片格式。
- 转换为 RGB。
- 处理透明背景。
- 限制过大图片尺寸。
- 保存预处理后的临时文件。

预处理不应改变用户上传的原始图片，原始图片仍然保留用于结果展示和历史记录。

## latex_formats.py

LaTeX 后处理负责让结果更适合网页展示和复制。

第一版可以包含：

- 去除多余空白。
- 去除不必要的外层 `$` 或 `$$`。
- 修正常见换行。
- 保留适合 KaTeX 渲染的纯公式内容。

结果页展示时可以同时提供：

```text
纯公式内容：\frac{a}{b}
Markdown 块公式：$$\frac{a}{b}$$
```

当前实现中，`latex_formats.py` 负责 LaTeX 规整、已知困难样例修正，以及 `raw`、`block`、`inline`、`render` 四种展示格式的生成。任务链路中的 Celery worker 在 `LATEX_POSTPROCESS` 阶段调用这些函数，页面只消费已经规整后的展示数据。

## 模型风险

PaddleOCR 和 pix2tex 都属于重依赖模型，可能涉及模型权重、图片处理库和网络下载。

第一版必须把模型风险隔离在 worker 和识别服务层。A 阶段进一步把模型风险隔离到可选的 FastAPI `model-api` 服务中。即使模型依赖出错，Django 页面也应能打开，历史记录页也应能展示失败任务。

错误信息应可见、可解释，而不是让整个网站崩溃。
