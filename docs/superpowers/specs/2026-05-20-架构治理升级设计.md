# 架构治理升级设计

Date: 2026-05-20

## 背景

Formula Lab 已经从课程实验原型扩展为论文公式识别工作台，包含识别任务、论文项目、公式资产、导出、系统监控和前端布局智能。当前真正占磁盘的大体积内容主要是本地缓存和模型文件，例如 `var/model-cache/`、`.pip-cache/`、`.conda/`、`node_modules/`、`media/`、`var/db.sqlite3`，它们已经被 `.gitignore` 排除。

更需要治理的是代码和文档的职责膨胀：`views.py`、`test_views.py`、页面 CSS、项目决策文档和历史计划文档开始变长。若继续加入 LaTeX preview、PDF preview、AI 校对和批量论文工作流，单文件维护成本会快速上升。

## 目标

1. 保持当前 Django 单 app 的迭代速度，同时建立清晰的内部模块边界。
2. 避免业务逻辑、页面样式、测试和文档继续堆成大文件。
3. 为后续论文项目、公式资产、导出预览、PDF/LaTeX preview 留出产品域边界。
4. 明确生成物、缓存、vendor 资源和手写源码的治理规则。

## 非目标

1. 本轮不拆成多个 Django app。
2. 本轮不重写 OCR 引擎、Celery、数据库模型。
3. 本轮不追求一次性目录大迁移，避免把可运行产品打散。
4. 本轮不新增大量长文档；新文档必须替代或压缩旧文档职责。

## 升级路线

### B. 仓库治理优先

先建立规则，再动代码。

- 缓存和运行产物继续保持 ignored：`var/model-cache/`、`.pip-cache/`、`.conda/`、`.venv*/`、`node_modules/`、`media/`、`*.sqlite3`。
- 生成物只允许通过命令生成，不手改：`apps/formulas/static/formulas/js/generated/layout-intelligence.js`。
- vendor 静态资源必须有来源命令：KaTeX 资源由 `scripts/copy_katex_assets.mjs` 复制。
- 建议文件阈值：
  - Python 业务文件超过 350 行需要评估拆分。
  - 测试文件超过 450 行需要按页面或产品域拆分。
  - CSS 页面文件超过 500 行需要抽出 components。
  - Markdown 决策文档超过 500 行需要归档历史段落或拆为索引。

### C. 产品域边界

先用代码目录表达产品域，暂不物理拆 app。

- Mission：单次识别任务、状态轮询、报告页、重试。
- Project：论文工作台、批量任务、公式资产聚合。
- Formula Item：单个公式的 LaTeX、质量状态、人工校正。
- Export：Markdown / TeX 导出，未来扩展 PDF preview。
- Ops：模型状态、warmup、健康检查、运行时诊断。

这些域通过 selectors、presenters、services 连接，不让 Django views 直接承担查询、格式化和业务编排。

## 数据流

1. View 只处理 HTTP 输入输出、权限和模板选择。
2. Selector 负责查询和聚合 ORM 数据。
3. Presenter 负责把模型对象转换为页面上下文。
4. Service 负责业务动作，例如识别、导出、格式化、健康检查。
5. Template 只消费稳定 context，不写复杂业务判断。
6. JS 只负责页面交互，不承担后端业务规则。

## 测试策略

- 拆分前先跑现有 `tests.formulas`，记录基线。
- 每次移动一个页面域，保证 URL、模板名、context key 和表单行为不变。
- 视图测试按页面拆分；服务测试继续覆盖 OCR、导出、格式化、模型状态。
- 每轮拆分后运行：

```bash
./.conda/bin/python manage.py test tests.formulas -v 2
make frontend-check
./.conda/bin/python manage.py makemigrations --check --dry-run
git diff --check
docker compose config --quiet
```

## 风险与边界

- 最大风险是“重构中顺手改产品行为”。本升级必须以行为不变为原则。
- 当前工作区存在并发 UI 改动，实施时需要先分组提交或明确哪些文件属于本轮。
- 不删除本地缓存，除非用户明确要求清理磁盘。
- 不把历史 plans 当作当前架构真相；当前真相应由 `docs/00-文档索引.md`、核心架构文档和本 spec 汇总。

## 交付顺序

1. 整理当前未提交改动，避免 report、workbench、projects 改动混在同一个架构提交。
2. 治理文档和生成物规则，压缩过长历史计划的入口权重。
3. 拆 views 和 view tests。
4. 抽 CSS components。
5. 抽共享前端 JS。
6. 建立 selectors 和 presenters。
7. 复核产品域边界是否稳定，再决定未来是否拆多个 Django app。
