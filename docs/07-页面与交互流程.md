# 页面与交互流程

## 页面列表

第一版 Mission Control 已有五个识别主流程页面，Product Core Foundation 增加 Projects-first 的两个页面：

- 首页
- Projects 页
- Project Workspace 页
- 进度页
- 结果页
- 历史记录页
- 系统状态页

另有一个错误状态视图，可以作为进度页或结果页的一部分实现。

## 页面深浅比例

Formula Lab 采用“入口 cinematic、工具页克制”的双层页面策略。Landing 可以承担品牌记忆、滚动叙事和高密度动效；进入真实工作流后，页面回到 SpaceX-inspired 黑白任务控制台和细网格工作台。

页面策略：

- 首页：Cinematic Landing，突出公式草稿、识别过程、论文工作区和进入 Workbench 的入口。
- Workbench 页：深色上传工作台，突出项目路由、图片预览、识别队列和开始识别。
- Projects 页：深色项目索引，突出论文项目、最近更新和进入工作区。
- Project Workspace 页：深色论文工作区，突出论文源码编辑、Formula Review Inbox、版本时间线和项目导出。
- 进度页：深色 launch sequence，突出阶段推进。
- 结果页：深色 LaTeX 控制台 + 白底公式渲染预览。
- 历史记录页：深色 mission log，记录项内部可使用浅色公式预览区域。
- 系统状态页：深色 telemetry，突出服务连通性和模型状态。

这个比例能保留 SpaceX 气质，同时保证 LaTeX 和公式预览的可读性。

## 全局导航

Formula Lab 采用 SpaceX-inspired 顶部导航任务控制台结构，不采用左侧侧边栏。

顶部导航包含：

- 左侧品牌区：`FORMULA LAB`。
- 右侧导航：`PROJECTS`、`WORKBENCH`、`MISSION LOG`、`SYSTEM`。

顶部导航的目标是让用户一进入页面就能看到核心功能，同时保留任务控制台气质。主导航不放模型状态灯，技术架构信息不直接堆在用户界面上，只有系统状态页用于展示 Docker、PostgreSQL、Redis、Celery 和识别模型的可用状态。

## 首页

首页是用户进入系统后的品牌化产品入口，不再承载上传表单。它的职责是用可滚动的 cinematic story 解释 Formula Lab 的产品想象：从公式草稿、OCR 识别、论文编辑、公式审查到协作信号，最后收束为明确的 Workbench 入口。

核心元素：

- 产品名称与核心叙事。
- Manuscript 纹理、公式场、公式流和液态幕布视觉主体。
- Scroll-driven 阶段：intro、absorb、center、decode、workspace、collab、paperExit、greenCurtain、greenCopy、blackCurtain、letterStorm、cta。
- 少量产品能力暗示：Formula Review Inbox、Paper Workspace、Collaboration Signals。
- 最终入口：进入 Workbench。

首页不直接展示 Docker、模型状态、上传锁定或任务队列。所有真实任务操作应进入 Workbench 后发生。这样 Landing 负责吸引与解释，Workbench 负责高效工作。

前端实现边界：

```text
frontend/formulas/landing/             React / GSAP / Three.js source
apps/formulas/templates/formulas/landing.html
apps/formulas/static/formulas/js/generated/landing*.js
apps/formulas/static/formulas/css/generated/landing.css
```

Landing 是 React island，不代表全站 SPA 化。它应能独立构建、独立回归，并且不影响 Workbench、History、Report、System 的普通页面运行。

## Workbench 页

Workbench 是真实上传和识别入口。

核心元素：

- 项目选择：Existing Project 或 New Project。
- 上传区域：支持点击选择和拖拽上传。
- 上传后在上传组件内部展示图片预览。
- 图片格式提示。
- 模型状态摘要和队列状态。
- 最近识别任务。
- `START RECOGNITION`。

Workbench 不承担 Landing 的强叙事动效，也不放过多技术说明。它的目标是让用户快速把公式图片挂到项目、创建 mission，并进入可观察的进度页。

mission 只在用户点击 `START RECOGNITION` 时创建。用户选择或拖拽图片后，页面只进入预览状态。

如果用户选择 Existing Project，系统会为这次上传创建一个 `BatchMission`，并把 `FormulaJob` 关联到对应 `PaperProject` 与 `BatchMission`。如果用户输入 New Project，系统会先创建 `PaperProject`，再创建批次和任务。识别成功后，Celery Worker 会自动把结果沉淀为 `FormulaItem`，Project Workspace 因此能立即展示 LaTeX Preview 与 Paper Fit Preview。

## Projects 页

Projects 页是 Product Core Foundation 的第一入口，用于从“单次识别任务”过渡到“论文项目管理”。

核心元素：

- 项目列表，按最近更新排序。
- 项目名称、Project Code、写作目标和默认导出格式。
- 项目下批次数、公式条目数、待审核数和可导出数。
- 空状态，提示创建或等待项目数据接入。
- 进入 Project Workspace 的操作。

这一页只负责 Projects-first 的项目索引，不实现 Crop Studio、导出文件或本地 LLM。

## Project Workspace 页

Project Workspace 是一个项目的论文公式资产工作区，承接 `PaperProject -> BatchMission -> FormulaItem -> PaperFile` 的页面能力。它不是后台表格，也不是单纯 OCR 结果列表，而是围绕论文源码、公式审校、版本轨迹和导出的工作台。

核心元素：

- 项目概览指标。
- Paper Workspace：论文文件树、CodeMirror 源码编辑器、源码预览和保存状态。
- Formula Review Inbox：可筛选的公式审查收件箱，展示 OCR 结果、当前 LaTeX、KaTeX Preview、状态和插入论文入口。
- Version Timeline：论文文件版本历史。
- Workflow Status：项目完成率、待审、可导出和最近批次。
- Paper Fit Preview：使用 Pretext 辅助估算公式在论文栏宽中的适配状态。
- Export Files，提供项目级 `.tex` 与 `.md` 即时下载。
- Symbol Intelligence 占位区，明确为后续阶段。

当前 Project Workspace 的服务端只负责页面骨架、项目概览、最近批次、导出入口和 React mount 配置。Formula Review Inbox、论文文件编辑、版本时间线和插入论文草稿由 React editor island 通过 JSON API 驱动。Paper Fit Preview 不是 PDF 编译结果，而是浏览器端的论文栏宽适配提示。Export Files 第一版是幂等 GET 下载，不创建持久化 `ExportArtifact` 记录，也不改变公式状态；Crop Studio、PDF 导出和本地 LLM 不在本阶段实现。

## 进度页

上传成功后进入进度页。进度页应像任务发射序列，而不是普通 loading 页面。

核心元素：

- 原始图片预览。
- 用户可读 Mission Code，而不是完整 UUID。
- 当前阶段说明，例如 `MODEL WARMUP`、`INFERENCE`、`RESULT READY`。
- 进度条。
- 状态徽标。
- 如果失败，展示错误原因。

前端每隔固定时间请求：

```text
GET /api/missions/<uuid>/
```

当 API 返回 `succeeded` 且进度为 100 时，页面自动跳转到结果页。

## 结果页

结果页是产品体验的核心。

核心元素：

- 原始公式图片。
- 识别出的 LaTeX 文本。
- 一键复制按钮。
- 网页公式渲染预览。
- Paper Fit Preview。
- 任务元数据。
- 返回首页按钮。
- 查看历史按钮。

LaTeX 源码区域使用深色控制台面板，公式渲染预览使用白底或高可读浅色区域。Paper Fit Preview 保留在 KaTeX Preview 下方，但作为低权重辅助仪表，不抢公式渲染和源码区域的主视觉。LaTeX 渲染使用 KaTeX。页面应同时展示“可复制文本”和“公式效果”，满足课程提升点要求。

LaTeX 控制台默认选中 `BLOCK` tab。用户可以切换 `RAW`、`BLOCK`、`INLINE`，复制按钮和渲染预览随当前 tab 更新。复制按钮在当前 UI 中使用图标按钮，通过 `aria-label="Copy LaTeX"` 保持可访问语义。

## 历史记录页

历史记录页用于展示所有识别任务，视觉上应像 mission log。

每条记录应包含：

- Mission Code。
- 图片缩略图。
- 任务状态。
- LaTeX 摘要。
- 创建时间。
- 识别耗时。
- 查看结果按钮。
- 复制按钮。

每条记录默认只展示总耗时。用户展开记录后，可以看到 `model_warmup_ms`、`image_preprocess_ms`、`inference_ms`、`latex_postprocess_ms` 等阶段耗时。

失败任务显示 `RETRY MISSION`。点击后创建新的 mission，并直接跳转到新 mission 的进度页。

历史记录页应支持空状态。当没有任何任务时，展示一个清晰的上传入口。

## 系统状态页

系统状态页用于开发和验收时排查问题，不作为普通用户主流程。

它应像 telemetry 页面，展示：

- Django Web 是否可访问。
- PostgreSQL 是否连接成功。
- Redis 是否连接成功。
- Celery worker 是否在线。
- 当前识别模型是否可加载。
- 最近一次识别任务是否成功。
- `WARMUP MODEL` 操作。

这个页面可以帮助快速判断问题属于页面、数据库、队列、worker 还是模型依赖。

`WARMUP MODEL` 只出现在系统状态页，不放在 Landing 或 Workbench。

## 交互原则

Formula Lab 的交互应遵循：

- 上传后立即给出反馈。
- 进度状态用后端数据驱动。
- 成功结果容易复制。
- 错误信息清楚，不让用户猜。
- 页面信息密度适中，避免课程作业感过重。
- 顶部导航保持克制，不把技术标签堆在主界面。
- 图标按钮和文字按钮各司其职，复制、重新识别、查看历史等高频动作要明显。
- 不让 SpaceX 气质压过实际工具可用性。
