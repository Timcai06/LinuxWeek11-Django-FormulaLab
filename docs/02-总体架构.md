# 总体架构

## 架构目标

Formula Lab 的架构目标是让一个公式识别网站同时满足三个条件：

- 可以在课程验收环境中稳定运行。
- 具备现代 Web 应用的真实工程结构。
- 后续可以替换识别模型、扩展历史记录和增加更复杂的任务处理能力。

## 总体结构

```mermaid
flowchart TD
    A["浏览器"] --> B["Django Web 应用"]
    B --> C["PostgreSQL 数据库"]
    B --> D["Redis 消息队列"]
    D --> E["Celery Worker"]
    E --> F["公式识别引擎"]
    E --> C
    B --> G["媒体文件存储"]
    B --> H["KaTeX / Pretext 前端预览"]
```

系统由四个主要服务组成：

- `web`：Django Web 服务，负责页面、上传、API、历史记录、项目工作区和导出下载。
- `worker`：Celery 后台任务服务，负责调用公式识别模型。
- `db`：PostgreSQL 数据库，负责保存任务和识别结果。
- `redis`：Redis 服务，负责 Celery 消息队列。

## 请求处理思路

用户上传图片时，Django 不直接在请求中执行模型推理。Django 只负责保存图片、创建 `FormulaJob` 记录，并把任务投递给 Celery。

后台 worker 收到任务后执行识别，并持续更新数据库中的任务状态。前端进度页通过 API 轮询任务状态，任务完成后跳转到结果页。如果任务挂载到 `PaperProject` 和 `BatchMission`，识别成功后会沉淀为 `FormulaItem`，进入 Project Workspace 的公式队列和导出流程。

这种设计避免了耗时识别阻塞 HTTP 请求，也让进度条有真实的后端状态来源。

## 分层设计

项目按以下层次组织：

```text
Presentation Layer     页面与交互
Web Application Layer  Django view、URL、API、页面 presenter
Query Layer            selector 负责查询和预加载
Domain Layer           FormulaJob / PaperProject / BatchMission / FormulaItem
Async Task Layer       Celery 任务
Recognition Layer      PaddleOCR / pix2tex 识别引擎适配
Layout Layer           KaTeX 渲染与 Pretext 文本布局测量
Infrastructure Layer   Docker、PostgreSQL、Redis、媒体文件
```

每一层只承担自己的职责。Django view 不直接了解 PaddleOCR 或 pix2tex 的内部细节，Celery task 也不直接处理页面展示逻辑。项目已经开始把较厚的页面逻辑拆入 `views/`、`selectors/` 和 `presenters/`，下一轮架构升级应继续收紧这个边界。

## 工程命名与界面叙事

Formula Lab 在工程层保持清晰命名，在界面层使用 Mission Control 叙事。

工程层：

```text
FormulaJob        一次公式识别任务
Celery task       后台识别任务
Recognition stage 识别阶段
System health     系统健康状态
```

界面层：

```text
Mission              一次可观察的识别任务
Recognition sequence 识别序列
Launch sequence      进度阶段展示
Mission log          历史记录
Telemetry            系统状态
Mission report       识别结果页
Control console      LaTeX 源码面板
Payload preview      公式渲染预览
Mission code         用户可读任务编号
```

这样可以同时满足两个目标：

- 代码和数据库模型不被过度装饰，便于维护。
- 用户界面形成统一的 SpaceX-inspired Mission Control 产品气质。

任何实现时，如果工程命名和 UI 文案冲突，应优先保证代码层清晰，UI 层通过模板文案完成产品叙事。

## Mission ID 展示策略

数据库内部可以继续使用 UUID 作为 `FormulaJob.id`，因为它适合作为主键、路由参数和后台关联字段。但 UUID 不适合作为主要用户界面标识，看起来像哈希码，降低产品质感。

用户界面应展示单独的 `mission_code`，例如：

```text
FL-20260519-0007
```

推荐方案是新增数据库字段 `mission_code`，在创建任务时生成并保证唯一；URL 和 API 可以暂时继续使用 UUID，页面标题、历史记录、报告页和进度页都显示 `mission_code`。这样可以同时保留工程稳定性和更好的产品体验。

## Projects-first 产品核心

Formula Lab 已经从单张图片识别扩展为 Projects-first 结构：

```text
PaperProject
  -> BatchMission
    -> FormulaItem
      -> optional FormulaJob
```

`FormulaJob` 仍然代表一次模型识别任务，`FormulaItem` 才是论文工作区中的长期公式资产。Project Workspace 当前承担公式队列、Inspector、Paper Fit Preview、Review Drawer、状态筛选、分页和项目级 `.tex/.md` 导出。这个边界很重要：后续架构升级不应把所有逻辑继续堆回 mission report 页面，而应围绕 FormulaItem 做审校、导出、质量评分和符号智能。

## Pretext 布局辅助边界

前端已引入 `@chenglou/pretext`，但它的定位不是替代 TeX 或 KaTeX，而是提供文本测量和布局辅助：

- 估算 LaTeX 摘要在列表中的行数和截断。
- 估算公式在论文栏宽中的 fit 状态。
- 减少 Mission Log 和 Project Workspace 中长文本造成的布局跳动。

Pretext 相关代码应保持在前端 layout intelligence 层，不参与 OCR 识别，不写入业务数据库作为唯一真相。数据库保存公式结果和审校状态，浏览器端负责预览与布局提示。

## 为什么使用 Celery

公式识别属于耗时任务，模型首次加载也可能很慢。如果直接在 HTTP 请求中执行识别，浏览器会长时间等待，甚至出现超时。

Celery 的作用是把耗时任务从 Web 请求中拆出去：

- 上传请求可以快速返回。
- 识别过程可以在后台执行。
- 前端可以展示真实任务阶段。
- 失败任务可以记录错误信息。
- 后续可以扩展重试、批量任务和队列管理。

## 为什么使用 PostgreSQL

Formula Lab 需要保存历史记录、任务状态、识别结果、错误信息和耗时统计。这些都是业务数据，应该放在可靠的关系型数据库中。

PostgreSQL 的优势是：

- 稳定可靠，适合真实 Web 应用。
- 与 Django ORM 配合成熟。
- 后续可以扩展更多结构化查询。
- 与 Docker Compose 组合清晰。

## 为什么 Redis 不保存业务数据

Redis 在本项目中只负责消息队列和 Celery backend，不作为业务数据库。业务数据统一写入 PostgreSQL。

这样可以避免数据来源混乱：

```text
PostgreSQL = 可信业务状态
Redis      = 任务队列和临时状态
```

如果 Redis 重启或清空，历史识别记录仍然保存在 PostgreSQL 中。

## 下一轮架构升级方向

当前主要架构风险不是服务选型，而是前端和页面层文件继续变大。下一轮升级建议聚焦：

- 拆分较大的页面 CSS，例如 `projects.css`、`result-inspector.css`、`workbench.css`。
- 页面 JS 继续模块化：Project Workspace、Result 和 System 已拆入各自目录；下一步聚焦 Workbench 以及 CSS 大组件。
- Django views 已开始收敛为 HTTP 编排；Projects 与 Project Workspace 的查询和页面上下文已进入 selectors/presenters。
- FormulaItem 审校确认已进入 `services/project_items.py`；下一步把导出状态流转、项目级 artifact 生成继续收敛进 services。
- 保持 repository governance checker 作为护栏，避免运行时缓存、媒体文件、虚拟环境和生成物污染源码边界。
