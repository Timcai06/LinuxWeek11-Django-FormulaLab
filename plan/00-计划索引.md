# Formula Lab 架构升级计划索引

## 目标

本目录用于沉淀 Formula Lab 下一阶段架构升级计划。当前路线已经从单纯的“先 A 后 B”推进为：

```text
已完成基础架构升级：
A：FastAPI 模型服务化
B：React / CodeMirror 编辑器岛

下一阶段产品路线：
B2：Pretext 第二阶段，公式审查收件箱
C：论文旁路 AI 助手
D：协作审阅房间
```

这不是一次全栈重写，而是在现有 Django + Celery + Redis + PostgreSQL 架构上增加两个清晰边界：

- A 阶段把重模型推理从业务进程中隔离出来，提升部署稳定性和后续扩展能力。
- B 阶段只在 Project Workspace 中引入 React 富编辑器，不替换全站 Django 模板。
- B2 阶段把 Pretext 从单点测量工具升级为前端布局智能层，优先服务 Formula Review Inbox。
- C / D 阶段围绕论文上下文做 AI sidecar 与多人审阅，不急着复刻完整 Overleaf。

## 当前架构原则

Formula Lab 继续保持以下原则：

- Django 是产品后端和业务中枢。
- Celery 是任务编排层，不直接承载页面交互逻辑。
- FastAPI 只做模型推理服务，不直接写业务数据库。
- React 只做编辑器岛，不把 landing、history、system、report 全部改成 SPA。
- PostgreSQL 是唯一业务数据真相。
- Redis 只作为队列和临时状态。
- Pretext 继续作为前端布局智能，不进入 OCR 结果真相链路。
- CodeMirror / React 只承载复杂编辑与交互，不把全站推成 SPA。
- AI 能提出建议，但论文源码与公式版本必须可审计、可回滚。

## 不做的事情

当前阶段明确不做：

- 不把整个 Django 项目改成 FastAPI。
- 不把全站改成 React/Vue SPA。
- 不让 FastAPI 直接操作 `FormulaJob`、`FormulaItem`、`PaperProject` 数据库表。
- 不让 React 直接绕过 Django API 写数据库。
- 不为了引入新技术破坏现有课程验收路径。
- 不在 Formula Review Inbox 阶段立即做多人实时协同。
- 不在 AI sidecar 阶段让 AI 自动静默改写论文正文。
